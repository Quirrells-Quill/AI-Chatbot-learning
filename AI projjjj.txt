## Other considerations & suggestions (design & pipeline)

Below are practical considerations and suggestions so the changes actually work well in practice.

1. **Preprocess PYQs (PDF → text):**

   * If your PYQs are PDFs, you need a PDF→text step (e.g., `pdftotext`, `pdfminer`, `pytesseract` for scanned PDFs). Add a `scripts/convert_pyqs.py` that converts each PDF into `.txt` inside `PYQ_DIR`. The final prompt must include only concise extracts (title, year, typical question stems) — not entire PDFs.

2. **Prompt size / truncation:**

   * You already have `MAX_PROMPT_CHARS`. When appending many PYQs, keep only a short extract per paper (e.g., first 2–3 questions) or produce an automatic PYQ *summary* locally (script that extracts question stems and topics) and include that instead of the whole PDF text.

3. **Security & privacy for local model:**

   * If you enable `OLLAMA_ENABLED`, ensure the local model (and the host) is properly sandboxed, and that sensitive data is not inadvertently logged.

4. **Question pattern generation guidance:**

   * The reasoner prompt should include explicit examples of each pattern you expect (example MCQ, example reasoning question, example TF, example match), plus how to format `answer_explanation` and `correlated_feedback`. Models follow examples well.

5. **Storing mapping from bullets → ids:**

   * When generating lesson bullets, add stable indices (0..n-1). Then the grader can point to these indices in `correlated_feedback`.

6. **Evaluation robustness:**

   * `evaluate_answers_with_reasoner` should normalize multiple answer formats (letters A/B vs indices 0/1 vs full-text answers). You already have some local fallback logic; expand it to canonicalize answers first.

7. **Human oversight & QA:**

   * For high-stakes assessments, add a review step (or flag questions generated from PYQs as "modeled on PYQ X, Y" so a human can validate).

8. **Logging & debug:**

   * Keep `debug_log_raw` outputs for new calls (PYQ loaders, call_ollama) to help debugging.
